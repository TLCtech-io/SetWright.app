# 002: Row-level security

Covers `supabase/migrations/20250101000002_rls.sql`: the auth helpers, the table grants, all 54
policies, and `casting_visible`.

Isolation is by membership. A user reaches a row when they hold an active `member` row in that
row's active ensemble, and their tier on that membership decides writes. There is no tenant id in
the session and no session variable. The app narrows a screen by filtering `ensemble_id`; RLS
draws the hard boundary, which is why `core` carries no `ensemble_id` at all.

The 64 migrations this file replaced are in `supabase/migrations/_archive/`. Numbers below refer
to files there.

## Peer visibility is the product, not a leak

Any active member can read every other member's availability, their casting assignments, and the
attendance record for their ensemble. `availability_read`, `attendance_read` and the
`casting_visible` view are all tenant-wide SELECT. That is intended, and it has caused at least
one reviewer to read the model as an over-broad policy. It is not a bug and it is not an
oversight from the era before the narrower reads landed.

Two reasons, both product decisions rather than technical ones.

- **Advance knowledge.** A singer needs to know who else will be at Thursday's rehearsal or
  Saturday's gig before deciding what to prepare and whether to go. The member schedule page
  says so in shipped copy: "Let your director know whether you can make each one, and see who
  else is coming" (`apps/web/app/e/[ensembleId]/me/schedule/page.tsx`).
- **Self-policing.** RSVPs and attendance that peers can see are the group's own pressure on
  turning up. A record only the director sees turns attendance into a discipline matter between
  one member and the director. A record the section sees is a shared expectation.

Casting works the same way. A member reads who else covers their part through
`casting_visible`, which is what `listMyPartCoverage` uses to tell them whether a part has
backup and who that backup is.

Attendance is the one where the app is currently narrower than the policy. The only read of the
table is `getAttendance`, on the director path through `buildRehearsalRecordView`. That is the
intended direction rather than a gap to close by tightening: the policy states the model, so a
member-facing attendance view is UI work with no migration behind it.

### What is deliberately not peer visible

The line is drawn at private judgement and contact data, not at scheduling facts.

- Another member's `self_reported_confidence`, unless the ensemble sets
  `confidence_visibility = 'shared'`. `casting_visible` nulls it otherwise.
- `director_assessed` and `learned_at`, director-only in every case. A member never sees the
  director's read of anyone, including themselves.
- Pending invite email addresses and token hashes, which live in `member_invite` under a
  director-only policy.
- The director's drafting space: `program` and `program_item`.
- Setlists that are not published, performed, or explicitly shared, and every draft child row.

### Narrowing any of these fails silently, which is the real trap

`apps/web/lib/attendanceGroups.ts` buckets any member with no visible availability row as
`pending`, which `MemberCallSheet` and `MySchedule` both render as "No reply". A row filtered by
RLS and a row that was never written are identical to the client: PostgREST returns rows, not a
denied count. Narrow `availability_read` to self-only and nothing throws. Both member screens
just start reporting that the entire group failed to reply.

Nothing pins this today. No test asserts that a member sees a peer's availability row, so the
tripwire is missing at the layer where the assumption lives. The guard belongs in the integration
tier against real RLS. It does not belong in the projection: teaching `attendanceGroups` to tell
"not visible" from "not answered" needs a second privileged source of member ids, a fourth
bucket, and new member-facing copy for a state that is permanently empty while the policy stays
tenant-wide.

## The helpers are SECURITY DEFINER because the model does not close otherwise

A policy that guards a row has to read `member` to check membership. `member` needs the same
guard, so its policy would read `member` to decide whether you can read `member`. That recurses.
`auth_member_tier` and `auth_is_self` read membership with RLS off inside them, which breaks the
cycle. This is not a performance choice. Without it there is no working policy set.
`auth_is_platform_admin` is definer for the same reason plus symmetry, so it can be called from a
policy or an RPC without recursing, even though no policy calls it today.

The hardening on all three is the pinned `search_path` (`pg_catalog, pg_temp`, not `public`, with
`pg_temp` last) plus full schema qualification of every table in the bodies. A caller with
temp-object rights cannot shadow a relation a definer function trusts.

One asymmetry an audit will notice. Only `auth_is_platform_admin` carries a
`revoke all ... from public` and an explicit grant to `authenticated`. `auth_member_tier` and
`auth_is_self` keep the default PUBLIC EXECUTE, in the archive and in the live catalog. Executing
them as `anon` yields null and false, since both key off `auth.uid()`, so the exposure is
nothing. It was never argued for in a migration header; it is left as found.

## Archiving a tenant had to freeze two things, not one

`auth_member_tier` originally checked only the member's status (002). A suspended or archived
ensemble kept full read and write, so archiving a tenant was cosmetic. 023 added the join to
`ensemble` with `e.status = 'active'`, which transparently denies every policy built on the tier.
028 found the matching hole in `auth_is_self`: with only member status checked, direct
availability writes still passed in an archived tenant.

Self-READ is a deliberate exception. It does not go through `auth_is_self`. `member_read` carries
its own `user_id = auth.uid()` branch, so a member still sees their own seat in an archived
tenant even though they can no longer write anything.

The consequence, recorded at the time and still true: archiving or reactivating an ensemble needs
a direct SQL path, because no route or RPC writes `ensemble.status`. The column defaults to
`active`.

## Grants decide whether, policies decide which

Migrations run as `postgres`, whose default privileges confer only
REFERENCES/TRIGGER/TRUNCATE/MAINTAIN on new tables to the API roles. Only `supabase_admin`'s
default privileges confer DML. Without the blanket
`grant select, insert, update, delete on all tables in schema public to authenticated`, a signed-in
user hits "permission denied for table" before RLS is ever consulted.

Our migrations grant `anon` nothing, and `anon` therefore reaches no tenant table. The live
catalog still shows `anon` holding REFERENCES/TRIGGER/TRUNCATE on every table, from the
instance's own `ALTER DEFAULT PRIVILEGES`. That is Supabase base setup, present on a fresh stack
before 001 runs, and none of it is DML.

### The app_user column pin blocks self-promotion

`authenticated` holds blanket table-level UPDATE and `app_user_update` lets a user update their
own row. Together they would let anyone PATCH `is_platform_admin = true` on themselves through
PostgREST. Column privileges are checked independently of RLS, so 055 revokes UPDATE and re-grants
it on `(email, display_name)` only.

Be precise about who can still write the flag. Not `service_role`: it holds no DML on `app_user`
at all and cannot even read the table. The only way in is a superuser or table-owner connection,
in practice `postgres` running SQL. "service_role and the SQL bootstrap" is one actor, not two.
The app never PATCHes `app_user` directly, since profile edits go through the `update_my_profile`
definer RPC, so the pin narrows nothing in use.

### The same technique was rejected for member (060)

A column-privilege pin on `member` would have to be re-derived every time a member column is
added. Getting it wrong breaks director roster editing at runtime with a privilege error that no
offline gate catches, because `npm run verify` never applies SQL. `member` got a trigger instead,
in file 003.

### invite_rate_event is deny-all on purpose

RLS on, no policies, and `revoke all ... from authenticated, anon` after the blanket grant. The
definer rate-limit functions are the only path in. The counter lives in Postgres rather than in
memory because in-memory limiting does not hold on Vercel Fluid Compute, where state is
per-instance and resets on a cold start.

One thing that revoke does not reach: the identity sequence. `invite_rate_event_id_seq` still
grants UPDATE to `anon`, `authenticated` and `service_role` from the instance default privileges,
so those roles can call `nextval`. Harmless, since with no privilege on the table there is nothing
to insert and `nextval` yields only a number. Recorded so nobody reads the revoke as covering more
than it does.

## Composition traps

**Permissive policies OR together.** Adding a policy to a table can only widen access, never
narrow it. This is why 041, 042 and 051 each drop and recreate rather than adding. To narrow a
read you replace it.

**A FOR ALL policy's USING applies to SELECT.** The common write policy therefore also confers
read to a director independently of the read policy. Two consequences: a director's read
visibility does not disappear if a read policy stops naming directors, and conversely, taking
director SELECT out of both policies at once breaks invoker RPCs whose DELETE carries a WHERE over
the table's own columns, which then silently match zero rows.

**A membership check must gate every branch of a multi-branch read.** `setlist_read` is
`membership AND (director OR published OR performed OR share_draft)`. Move the membership term
into the OR list and a bare `published_at is not null` matches rows in every ensemble. That is a
cross-tenant leak from one pair of parentheses. The same shape is in `setlist_item_read` and
`setlist_break_read`. The archive warns about it twice, in 041 and again in 051 when a third
branch was added.

**`casting_select_director` is load-bearing, not redundant.** A filtered casting write
(`DELETE` or `UPDATE ... WHERE part_id in (...)`) needs its target rows visible through a SELECT
policy. Delete this policy on the grounds that directors read through the view anyway and director
casting edits break with no error at all, only empty results.

**Do not replace the written-out policies with a generator loop.** The loop is shorter, but five
of the policies it produced are later narrowed (`program`, `program_item`, `setlist`,
`setlist_item`, `setlist_break`), so a loop has to be followed by overrides and the final shape of
a table lives in two places. Written out, each policy's live form is one greppable statement that
lines up with one row of `pg_policies`. The cost is the near-identical statements for the
member-reads-director-writes pattern, and on this file that is the right trade.

## Setlist: two member paths, and children narrower than the parent

Members reach a setlist two ways. Publish freezes the order into `published_order` and is the
final record. Share-draft (051) is opt-in, reversible, and stays current as the director edits.
`setlist_read` allows both.

`setlist_item_read` and `setlist_break_read` allow only published-or-performed. The gap is
deliberate: a member reads a shared draft from the snapshot column on the setlist row, never from
the child rows, so no member sees a draft item or break. The child policies name the parent's gate
explicitly in a subquery rather than leaning on `setlist_read` composing through, which means
tightening the parent does not silently tighten the children.

`program` and `program_item` went director-only after the fact, in 042. The page layer bounced
members and the API required a director, but the common read pattern still let a member SELECT
these straight through PostgREST and see the proposed order and the open/close/keep pins. That was
within-tenant visibility, never a cross-tenant leak.

## member_invite is a side table because RLS is row-level

`member_read` lets any active member select the whole `member` row. While the invite state lived
on that row, a plain member could read a peer's pending invite address through the Data API, and
app-layer masking does not stop a raw PostgREST query. 047 moved the invite state to a
director-only side table so RLS is the enforcement rather than the app projection.

The invitee cannot read their own invitation through this policy, because they hold no member row
yet. Four SECURITY DEFINER functions in 007 cover that, and being definer is precisely how they
get past `member_invite_read`: `list_pending_invitations`, `accept_invitation`,
`decline_invitation` and `refresh_pending_invite`. The first three key on the caller's own
`auth.email()`. `refresh_pending_invite` does not: it takes the address as an argument and is
granted to `service_role` only, for the unauthenticated resend route. Do not read the four as one
uniform shape.

## casting_visible and the security barrier

Ownership of a casting row is per column. The director owns the assignment, `is_primary` and their
own assessment; the member owns `self_reported_confidence`. RLS is row-level and cannot split
that, so members get no SELECT policy on the base table and read through the view instead. They
keep the base-table SELECT privilege from the blanket grant, which is required for
`casting_select_director` and the director's filtered writes to resolve rows, but the privilege
alone yields zero rows. That is what makes `private` actually hold rather than being a UI nicety.

The barrier was measured before it shipped, and it was held back from the review it belonged to
until it had been. A barrier view refuses to push caller quals down unless they are leakproof, and
the drafter's hottest read goes through this view. The fear was that the ensemble filter would
stop reaching the base scan, turning the castings CTE into a cross-tenant scan of `casting` with a
per-row definer call.

Measured on a seeded stack as an authenticated director, against the shape the castings CTE uses:

- without the barrier: `Index Scan using idx_casting_part`, ensemble filter as a post-filter
- with the barrier: `Index Scan using idx_casting_ensemble`, ensemble filter as the index condition

Better, not worse. `(select ensemble_id from ev)` is uncorrelated, so it becomes an InitPlan
evaluated once to a constant and the qual reduces to a leakproof equality that is pushdown-safe
into a barrier view. A correlated sub-select would not be, which is what the general warning is
about. The remaining cost is that genuinely non-pushdown-safe quals stay outside the view; on this
view that is two `in (select ...)` predicates that already planned as joins.

Worth knowing what this did and did not close. There was no way to observe the pre-barrier shape
through PostgREST, which compiles filters to plain operators and offers no per-row error or notice
to leak through. The barrier closed a shape, not a live leak.

## The platform-admin flag grants no data access

`auth_is_platform_admin` gates the `/admin` surface and the admin-invite path. No policy in this
file references it, so a platform admin still cannot read another ensemble's rows. The flag is set
out of band by SQL because an endpoint that grants admin would be a privilege-escalation target.
